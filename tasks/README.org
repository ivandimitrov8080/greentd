* How to work in this directory
  :PROPERTIES:
  :ID:       meta-howto
  :END:

  This directory is the single source of truth for *what is left to build*. It
  is a plan written against the code that already exists in =src/=, not against
  an imagined greenfield project. Every task names the file it touches.

  Workflow:

  1. Read the *Milestones* section to find the current milestone.
  2. Open the file for the subsystem, find the highest-priority =TODO= that is
     not =BLOCKED=, and move it to =NEXT=.
  3. On completing a task, tick its acceptance checkboxes, set it to =DONE=,
     and update =:STATUS:= in the file header if the subsystem is finished.

  Run =C-c a= style agenda?  No. This project has no org agenda config; entries
  are meant to be read as a checklist. Use =org-todo= and =org-cycle= normally.

** Task format (mandatory)
   :PROPERTIES:
   :ID:       meta-format
   :END:

   Every task heading is written exactly like this:

   #+BEGIN_SRC org
   ** TODO [#A] Imperative title, no trailing period          :@sim:
      :PROPERTIES:
      :ID:         widget-004
      :EFFORT:     1d
      :BLOCKED-BY: widget-001
      :END:
      Why this exists, in one or two sentences. Cite the WC3 behaviour being
      reproduced, or the defect being fixed, by ID (=D12=).

      - Files: =src/sim.rs=, =src/game.rs=
      - Acceptance:
        - [ ] Concrete, testable statement.
        - [ ] Another one.
   #+END_SRC

   Rules:

   - =ID= is unique across the whole directory, =subsystem-NNN=, lowercase.
   - =EFFORT= is a rough sizing: =2h=, =1d=, =1w=. It is a schedule input, not
     a promise.
   - =BLOCKED-BY= lists IDs that must be =DONE= first. =BLOCKS= is the inverse
     and is optional (it is derivable, so do not bother keeping it in sync).
   - Priority =A= means correctness, faithfulness or blocking; =B= means
     meaningful gameplay; =C= means polish. Anything that can lose a player's
     match data or let a client cheat is =A= by definition.
   - Acceptance criteria must be checkable without reading the diff. "Feels
     better" is not an acceptance criterion.
   - Do not use =#+TODO:= inside a task file to invent new keywords. The four
     active states are =TODO NEXT IN-PROGRESS WAITING BLOCKED=.

** Effort vocabulary
   :PROPERTIES:
   :ID:       meta-effort
   :END:

   | Level | Meaning                                                |
   |-------+--------------------------------------------------------|
   |     2h | one sitting, one file, no design decisions left open  |
   |     1d | one file plus its tests, one design decision           |
   |     1w | new subsystem, multiple files, protocol or data-model change |
   |     1m | multi-week epic; should be split before starting       |

** Implemented
   :PROPERTIES:
   :ID:       status-implemented
   :END:

   - One crate with a library root and a thin binary: the three run modes share
     one =App= builder in =src/main.rs=, and =src/lib.rs= owns the modules so
     =tests/= can link them.
   - =src/sim/=: server-only authoritative state machine, split into `mod.rs`, `waves.rs`, `combat.rs`, `economy.rs` and `rng.rs` (found-005). =HashMap= of
     =CreepId -> Creep=, =IVec2 -> Tower=, =PlayerKey -> Player=. Plain
     =step(dt) -> Vec<SimEvent>=, no networking types, unit-tested headless by
     [[file:12-testing.org][12-testing.org]] =test-001= (see =tests/sim_smoke.rs=).
   - Creep model: distance-along-path, =hp/max_hp=, =base_speed=,
     =slow_mult=+ =slow_timer=, =bounty=, =last_hit_by=.
   - Wave loop: infinite, 20 s between waves, first wave at 3 s, both from =assets/balance/match.ron=. Count is
     =(4 + wave/2) * connected_players=; =hp = 45 * (1 + 0.28*(w-1))=;
     =speed = 55 + 2*(w-1)=; =bounty = 6 + w/2=. Creeps are spread evenly
     around the whole loop.
   - Tower model: =kind= 0/1/2 = Basic/Cannon/Frost, from =assets/balance/towers.ron=;
     unbounded =level=; per-shot tier multipliers on damage, range and rate.
     Targeting picks the creep furthest along the path inside range. Cannon
     splashes, Frost slows.
   - =try_build/ try_upgrade/ try_sell/ call_wave= are the only mutators, each
     returning =Result<(), Reject>=.
   - Lose condition: =creeps.len() > =match_rules.overrun_cap= (=150= in
     =assets/balance/match.ron=)= ends the match permanently.
   - =src/map.rs=: 32x24 grid, =TILE = 32.0=, one closed ring path through four
     corner waypoints; buildability is "not within =0.95 * TILE= of the path".
   - =src/net/protocol.rs=: =ClientCmd= (C2S) and =ServerNotice= (S2C) messages (in =src/net/messages.rs=),
     one bidirectional reliable channel, six replicated components.
   - =src/net/server.rs=: player identity derived from the UDP peer address, one
     private =PlayerView= entity per player, one global =MatchView= entity,
     sim state mirrored into replicated entities every =Update= with
     change-diffing.
   - =src/net/client.rs= and =src/ui/hud.rs=: no prediction, no interpolation. Text HUD, keys 1/2/3,
     LMB build, U upgrade, RMB sell, Space calls the next wave.
   - =src/ui/visuals.rs=: orthographic camera with =AutoMin= scaling, 768 tile
     sprites, creep sprite darkened by HP fraction, tower sprite coloured by
     kind and scaled by level. Sprites are attached by =On<Add, ..>= observers.

* The single most important correctness question — two lineages
  :PROPERTIES:
  :ID:       lineage
  :END:

  "Green TD" is not one map. Two lineages share the name, and they have
  *different lose conditions*. The existing code picked one and its own comments
  assert it is "Green TD's real lose condition", which is only true of one
  lineage.

  | Lineage | Lineage A — "Green Circle TD" | Lineage B — "Green TD" / "Green TD PROs" |
  |---------+-------------------------------+------------------------------------------|
  | Author  | "hit" and many forks          | KaMiKaZePeNgUiN, later GenoHacker / Sencility |
  | Lose    | Too many creeps alive on the ring at once | Lives; a creep reaching the "Life Zone" leaks and costs lives |
  | Threshold | 600 / 700 / 800 / 1000 depending on version | Boss leak costs 10 lives; 0 lives = defeat |
  | Waves   | Endless                       | 36 waves (PROs) or 60 waves, then Endless |
  | Source  | hiveworkshop thread 350930    | hiveworkshop thread 249982, wc3maps 356685 |

  The current code implements Lineage A with =match_rules.overrun_cap = 150=
  (=assets/balance/match.ron=), which does not even match Lineage A's documented
  numbers (600–1000).

  **Decision:** support both, as data. The lose rule becomes a match setting
  (=lobby-003=) with two implementations (=sim-005=). Default for a fresh match
  should be Lineage B (lives), because "leak costs a life" is the mechanic most
  players remember and because it gives a longer, more forgiving ramp than a
  hard creep cap.

  This is not scope creep for its own sake: it is one enum, two match settings,
  and it prevents the project from being *wrong about the game it is cloning*.

* Cross-cutting decisions
  :PROPERTIES:
  :ID:       decisions
  :END:

** DONE Balance lives in data, not code                                  :@sim:
   :PROPERTIES:
   :ID:       decide-data-driven
   :EFFORT:   1d
   :END:

   All tower stats, creep stats, wave tables, ability numbers and drop rates
   move to RON assets under =assets/balance/=, loaded by both peers, hashed into
   the protocol version. Rationale: the original map's numbers were tuned by
   hand over years; this project needs to be able to do that without a
   recompile, and needs both peers to agree on the numbers or the "dumb client"
   model breaks (tooltips would lie).

   See [[file:00-foundation.org][00-foundation.org]] =found-004=.

** DONE Server is authoritative; the client never simulates                    :@net:
   :PROPERTIES:
   :ID:       decide-authority
   :END:

   Keep the existing model. A TD has no twitch input, so there is nothing to
   hide latency behind; prediction would add determinism obligations for no
   player-visible benefit. The client *does* get interpolation and a visual-only
   "ghost" of the tower it is about to place. This decision constrains
   [[file:09-networking.org][09-networking.org]] and [[file:10-ui.org][10-ui.org]] and should not be revisited
   without a concrete reason.

** DONE Pin the dependency set and write down the upgrade path              :@found:net:
   :PROPERTIES:
   :ID:       decide-upgrade-path
   :EFFORT:   2h
   :END:

   =bevy= and =lightyear= move together or not at all: lightyear 0.29 is written
   against bevy 0.19 and nothing else, so a bump of one is a rebuild of the
   other. Without a written procedure a version bump is an unbounded refactor,
   and without a pin the local and CI builds can disagree about which one they
   are building. This is the procedure; see [[file:00-foundation.org][00-foundation.org]]
   =found-008=.

   Pinned today (from =Cargo.lock=):

   | Crate     | Required | Resolved |
   |-----------+----------+----------|
   | bevy      | 0.19.1   | 0.19.1   |
   | lightyear | 0.29     | 0.29.0   |
   | ron       | 0.12     | 0.12.2   |
   | serde     | 1        | 1.0.229  |

   Edition =2024= needs rustc 1.85; lightyear 0.29.0 declares =rust-version =
   "1.95"=, which is the highest floor of any dependency and therefore the real
   one. =rust-toolchain.toml= pins =1.97.1=, the version the project is
   actually developed on, so the Nix devshell's =rustc= and CI's are the same
   binary.

   **Upgrade procedure**

   1. Read lightyear's release notes for the target version and find the bevy
      version they name. Bevy breaks API on every minor release and lightyear
      tracks it one-to-one, so the two are bumped in *one* commit. Raise
      =rust-toolchain.toml= in the same commit if the notes raise the MSRV.
   2. =cargo update -p bevy -p lightyear= -- never a bare =cargo update=, which
      floats every transitive crate at once and leaves no single suspect.
   3. =cargo build=, then re-check the plugin ordering in =src/main.rs=. The
      invariant is that =protocol::build_protocol(&mut app)= runs *after* the
      lightyear plugin groups and *before* any =Client= or =Server= entity
      exists: it fills a registry both halves read, and a peer created before it
      runs has no component table.
   4. Re-check the four feature groups in the =lightyear= entry in =Cargo.toml=:
      that each one still exists under that name, and that
      =default-features = false= is still what we want (the defaults enable
      =prediction= and =interpolation=, which =decide-authority= rules out).
   5. =cargo test=, then =cargo clippy --all-targets -- -D warnings=, then
      =cargo fmt --check=. The same three commands CI runs, in the same order.
   6. Run all three modes by hand: =cargo run= (host), =cargo run -- server=
      with =DISPLAY= unset, and =cargo run -- client= against it. A netcode
      change whose only symptom is a peer that never connects is exactly what
      this step catches.
   7. For any change to =src/net=/, re-run the remote pair with lightyear's
      message trace on and check that *both* directions appear:
      =RUST_LOG=info,greentd=debug,lightyear_debug::message=trace= on the server
      and the client at once, then grep for =message_send= and
      =message_receive_bytes= on each. This is step 6 with the instrument
      pointed at the wire, and it is here because =audit-030= (D32) was a
      two-word mistake that stopped every notice reaching a remote client while
      every test in =tests/= stayed green.
   8. Update the table above and the one in =Cargo.toml=, and say in the commit
      message which version was left behind.
