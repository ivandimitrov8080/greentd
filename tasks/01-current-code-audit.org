** DONE [#A] Run a host as a real lightyear host client                            :@net:
   :PROPERTIES:
   :ID:         audit-029
   :EFFORT:     1d
   :END:

   *D31, found while verifying =found-007=, and it is the reason =found-007= could
   not be finished first.* Host mode -- the default, =cargo run= -- ran a
   =RawClient= over a real UDP socket in the same =App= as a =RawServer=. That is
   not a host: lightyear calls it =NetworkTopologyError::MixedClientServer= and
   logs it as an error on the first frame, and in practice it took the process
   down about three seconds into wave 1 with

   #+BEGIN_EXAMPLE
   panicked at bevy_replicon-0.42.3/src/server.rs:323:
   registry should always exist on the server
   panicked at lightyear_replication::client::sync_entity_map:
   Parameter `Res<'_, ServerEntityMap>` failed validation: Resource does not exist
   #+END_EXAMPLE

   The mechanism: =lightyear_replication::client::sync_client_state= puts
   =bevy_replicon= into =ClientState::Connected= for any connected =Client= that is
   *not* a =HostClient=, so =receive_replication= runs -- and that system removes
   =ServerEntityMap= and =ReplicationRegistry= from the world for the duration of
   its run. The replicon *server* side is simultaneously =Running=, because the
   =RawServer= is =Started=, and its =buffer_removals= observer fires on every
   component removal and =expect= s the registry to be there. Two halves of one
   replication stack, each valid alone, in one world.

   - Files: =src/net/client.rs=, =src/net/server.rs=
   - Acceptance:
     - [x] =cargo run= (host) survives a full wave and a client connect with no =MixedClientServer= error and no panic.
     - [x] A host plus one remote client both run; the remote is still a real UDP peer.
     - [x] =cargo run -- server= and =cargo run -- client= are unchanged.
     - [x] A host client is not sent replication: no =Remote= marker, no duplicate =MatchView=, no duplicate creep.

   Fixed by using the mechanism lightyear provides for exactly this. A host spawns
   `(Client, LinkOf { server })` with *no IO component at all* and triggers
   =Connect=; =lightyear_connection::host::HostPlugin= recognises a client whose
   =LinkOf= points at a =Started= server and inserts =Connected=, =LocalId=,
   =RemoteId=, =ClientOf= and =HostClient= together. From then on:

   - messages flow in process. Both directions land on that one entity, because it
     is simultaneously the =Client= (=MessageSender<ClientCmd>=) and the
     =ClientOf= (=MessageSender<ServerNotice>=); =MessagePlugin::send_local= hands
     them straight to the matching receivers instead of building packets.
   - replication does not flow. =sync_client_state= skips a =HostClient=, so
     =receive_replication= never runs, so neither the resource-removal window nor
     the panic can happen, and no =Remote= is inserted. The entities the host
     renders are the server's own.
   - =on_client_connected= (=src/net/server.rs=) sees the same =Connected= +
     =RemoteId= + =ClientOf= shape a remote peer has, distinguishes it with
     =Has<HostClient>=, and creates its =PlayerView= *without* =Replicate=.

   Note =HostClient= is not re-exported in `lightyear::prelude`: the import is
   =lightyear::connection::host::HostClient=. And =spawn_client= had to move from
   =Startup= to =Update= with a latch, because a =LinkOf= needs the =Server=
   entity and two plugins' =Startup= systems are not ordered against each other.

   =audit-003= still owns the addressing policy; this task only made the host a
   thing that *can* be addressed. =net-006= is the same fix described at the level
   of the network design and closes with this.

** DONE [#A] Rate-limit commands with a per-peer token bucket                         :@net:
   :PROPERTIES:
   :ID:         audit-007
   :EFFORT:     1d
   :BLOCKED-BY: audit-001
   :END:

   D7: =handle_cmds= (=src/server.rs=) drains =recv.receive()= and executes every
   queued command in the same frame, so the only bound is how many arrived. A host
   that accepts thousands of build attempts per tick is a denial of service against
   everyone's match.

   - Files: =src/server.rs=, =src/game.rs=, =src/config.rs=
   - Acceptance:
     - [x] A token bucket per peer refills at a rate and burst fed from =Config= (found-002) and is consumed once per command.
     - [x] Over-budget commands are dropped, not deferred, and exactly one =Reject::RateLimited= notice is sent for the frame (uses audit-001's variant).
     - [x] Test: bursting =n + burst= commands in one frame yields exactly =burst= executions.
     - [x] The rate and burst are configuration, not literals in =server.rs=.

   =src/ratelimit.rs= is the whole policy: a ~30-line =TokenBucket= that holds
   =burst= tokens, earns =commands_per_second * dt= per frame and spends one per
   command. It is deliberately pure -- it knows nothing about peers, commands or
   sockets -- so =tests/ratelimit.rs= drives it a frame at a time and states the
   acceptance box above directly, with no =App=. =handle_cmds= keeps one bucket
   per =PlayerKey= in =Net::buckets=, settles the frame's refill once, splits the
   drained queue into "afforded" and "over budget", executes the first and
   *drops* the second (a deferred command is the backlog the bucket exists to
   prevent), then sends exactly one =Reject::RateLimited= however far over
   budget the peer went. Buckets are created on connect and dropped on
   disconnect, so an unregistered peer still has no bucket and no way to act
   (D8).

   =command_burst= (=16=) and =commands-per-second= (=20=) are =Config= fields, so
   a stress run is a flag rather than a rebuild. The rate is per second rather
   than per tick because =handle_cmds= runs in =Update=, where the frame delta is
   what the clock gives it.

   Green: 8 tests in =tests/ratelimit.rs=, including
   =a_burst_taller_than_the_bucket_is_cut_down_to_the_bucket=, which is the last
   box stated almost word for word. The across-many-frames disconnect policy is
   =net-005='s, not this task's.

   =audit-006='s rule that "a refusal is never silent" was also checked against a
   live remote client rather than only in the sim. Four build attempts against

   deliberately flooding, and no manual run does that.

** DONE [#A] Stop replacing a peer's MessageManager when it connects                :@net:
   :PROPERTIES:
   :ID:         audit-030

   *D32, found while running a server and a client side by side to verify =found-007=,
   and it had been silently discarding every notice sent to a remote player.*

   =on_client_connected= (=src/net/server.rs=) opted a new connection into
   messaging by inserting =MessageManager::default()= alongside the rest of the
   link components. =MessageManager= is already a *required component* of both
   =MessageSender=M== and =MessageReceiver=M==, and each of those registers itself
   in that manager from a =#[component(on_add)]= hook:

   #+BEGIN_SRC rust
   // lightyear_messages-0.29.0/src/send.rs:257
   pub fn on_add_hook(mut world: DeferredWorld, context: HookContext) {
       world.commands().queue(move |world: &mut World| {
           let mut message_manager = entity_mut.get_mut::<MessageManager>().unwrap();
           message_manager.send_messages.push((MessageKind::of::<M>(), context.component_id));
       })
   }
   #+END_SRC

   So the entity *already* had a populated manager by the time this ran -- and
   inserting a second, default one replaced it. =send_messages= went back to
   empty, and =MessagePlugin::send= (which walks exactly that list) had nothing to
   serialize. Every =ServerNotice= was dropped inside the server's own process. The
   sender still existed, the channel still existed, the bytes were never written.

   *receiving* looks the message kind up in the global =MessageRegistry= and then
   fetches the component by id, so it does not consult the per-entity list at all.
   Client-to-server commands worked the whole time; server-to-client notices never
   did.

   - Acceptance:
     - [x] No system inserts a bare =MessageManager= on a connection; the one the engine inserts is left alone.
     - [x] A remote client receives =ServerNotice::WaveStarted= for every wave.
     - [x] A remote client receives a refusal, with its reason, when the server refuses one of its commands.
     - [x] The send and receive paths are re-verified against a running server and client, not against a host.

   Fixed by deleting the two words. Worth recording *how* it was found, because
   nothing cheaper worked: the sim tests cannot see it, the host run cannot see it
   (in-process delivery goes through =MessagePlugin::send_local=, which reads the

   stomp), and adding =info!= probes to =tick_sim= only proved the server *called*
   =send=. The line that settled it was lightyear's own:

   #+BEGIN_EXAMPLE
   $ RUST_LOG=info,greentd=debug,lightyear_debug::message=trace ./greentd server

* Sequencing

  Work top to bottom. The order is chosen so that each phase is safe to start on the
  code the previous phase left behind, and so that authority holes close before any
  new feature widens them.

  1. *Foundations of the audit.* =audit-010= (D17, the headless harness) and
     =audit-001= (D25, the =Reject= reasons) come first. Every later sim task adds a
     test, and the authority tasks need a reason to report. Neither changes behaviour
     on its own.
  2. *The [#A] authority cluster.* =audit-002= (D1/D2), =audit-003= (D3), =audit-004=
     (D4), =audit-005= (D5), =audit-006= (D6), =audit-007= (D7), =audit-008= (D8).
     These stop a client from draining or destroying another player's board, freezing
     the HUD, spamming waves or commands, or minting a zero-gold player. Do these
     before any feature work.
  3. *Identity, once =net-001= lands.* =audit-009= (D9) turns the socket address into
     a session identity; it is the prerequisite for reconnect and for the leaver rule
     to be trustworthy.
  4. *The wire-format batch, done together behind =net-001=.* =audit-009= (D9),
     =audit-011= (D18's balance hash), =audit-019= (D22) and =audit-020= (D23) all
     change or depend on the format, so doing them in one pass is cheaper than three;
     =audit-024= (D12, the component merge) joins this batch because it changes the
     replicated component set. None may start before =net-001= is =DONE=.
  5. *The design decision.* =audit-012= (D19) stays =WAITING= until
     =decide-default-lineage= is signed off. It blocks nothing else in this file, but
     it gates =sim-005=, and the lose condition cannot be finalised until it resolves.
  6. *The [#B] fidelity cluster.* =audit-013= (D10), =audit-014= (D11), =audit-015=
